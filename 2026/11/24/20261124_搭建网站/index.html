博客搭建

发表于 2026-11-24 更新于 2026-11-26 分类于 建站笔记
一台 Windows 电脑、一个域名，从 SSH 端口到 SSL 证书、再到绑定国内域名 pointwind.cn 的完整排错过程，把个人博客从零推上线。

写在前面

今天完成了一件拖延已久的事：搭建起一个真正属于自己的博客。

不是为了做号，也不是为了流量，只是想要一个地方：把踩过的坑、想明白的问题、读过的东西，按自己的结构写下来。平台笔记会跟着账号规则走，但一个自己的域名，是少数能真正“带走”的东西。

这篇文章不是精简教程，而是一份完整的搭建复盘：从选域名开始，到 Node.js、npm、Hexo、Git SSH、GitHub Pages，再到途中遇到的各种报错。命令均按实际执行顺序保留。

环境：Windows、Node.js v26.13.1 LTS、npm、Hexo、GitHub Pages
本地博客目录：D:\blog\pointwind
GitHub 仓库：point-wind/point-wind.github.io
当前地址：https://point-wind.github.io
自定义域名 pointwind.cn 已下单，待开通后再绑定（见第七步）

第一步：先想清楚“域名买什么”，而不是“哪个便宜”

先澄清两个误区：

  • 在国内注册商买域名同样要实名认证，不实名会被 ServerHold，解析将被暂停。海外注册商可免实名，但国内解析稳定性较差。
  • 域名 ≠ 服务器。域名只是门牌号，Hexo 生成的是纯静态文件，放在 GitHub Pages / Cloudflare Pages 上完全免费，云服务器按需购买。

在腾讯云或阿里云搜索目标域名并下单即可：

  1. 先买 1 年，待博客稳定更新后再一次性续到 5～10 年锁定价格
  2. 结算页勾选 自动续费（购买时优先关注续费价格）
  3. 付款后立即提交实名认证（身份证，1～3 天审核）
  4. 账户预留少量余额，避免自动扣款失败

第二步：搞懂 Node.js 和 npm，再动手

Node.js 下载页面的选项较多，初次接触容易混淆。先理清几者的关系。

基本概念

Node.js 是发动机。

JavaScript 原本只能在浏览器中运行。2009 年，Chrome 的 V8 引擎被独立出来，做成一个可在操作系统上直接运行的程序，并加上读写文件、访问网络、启动服务器等浏览器中不具备的能力——这就是 Node.js。

Node.js = V8 引擎（解释 JavaScript） + 系统能力（文件、网络等）

安装 Node.js 并非为了学习后端，而是因为目前几乎所有前端工具链都运行在 Node.js 上：Hexo、VitePress、Webpack、Sass、Babel……Hexo 正是将 Markdown 转换为静态博客的工具，它必须由 Node 驱动。

npm 是随 Node.js 一起安装的包管理器。

它负责三件事：

  1. 一个大型公共仓库（npmjs.com，300 万+ 开源包）——RSS、站点地图、数学公式、图片压缩等都有现成的实现；
  2. 一个命令行工具——npm install xxx 会从仓库把包连同依赖一起下载到本地；
  3. 一个 package.json 清单——记录“这个项目用了哪些包、什么版本”。

第 3 点是最实用的设计。package.json 相当于博客的配方单：换电脑时不用搬 node_modules（几百 MB、上万个文件），只要

就能原样复原。因此：node_modules 是可再生的产物，package.json 和 package-lock.json 才是需要保留的资产（后者是精确版本锁，不要删除，也不要写入 .gitignore）。

fnm 是 Node.js 版本管理器。

它可以同时安装 Node 20 和 Node 26，并按项目切换。功能实用，但对单一博客项目并非必需，而且不应与 MSI 安装包混用——两套并存容易出现“终端里的 node -v 与预期版本不一致”的问题。两种方式选其一即可，这里选择 MSI 安装包。

LTS 还是 Latest？

类型 特点 选它
LTS（长期支持） 稳定，插件兼容性好，安全维护周期长 ✅ 选它
Latest / Current 新特性先到，偶尔导致旧插件异常 暂不

教程中常见的 Node 18 / 20 并非强制要求，新建博客使用当前 26.x LTS 即可。稳定兼容优先于尝鲜。

两个原因叠加造成，并非部署失败：

1. GitHub 网页有缓存。 刚推送完，仓库首页可能仍显示 empty，刷新一下（或等待十几秒）就会出现 main 分支和 HTML 文件。

2. 本地分支叫 master，远程叫 main。 日志中 Branch 'master' set up to track remote branch 'main' 已说明原因：Hexo deployer 每次将 public/ 的内容强制推送到远程 main 分支，本地 master 只是中转。因此本地分支名称无关紧要，无需执行 git branch -M。

  • 地址是 https://point-wind.github.io，连字符 -

第七步：绑定国内域名 pointwind.cn

域名实名通过后，腾讯云控制台状态变为「正常」。当天把解析、验证、HTTPS 一次走完，https://pointwind.cn 已能正常访问。整体顺序是：先在 GitHub 登记域名并验证所有权 → 再到腾讯云加解析记录 → 最后开 HTTPS。顺序不能反：只配 DNS 而不在 GitHub 登记，域名可能被别人抢先绑定到他的仓库。

前置确认

  • 域名状态：腾讯云 → 域名管理，实名审核通过。未实名会被 ServerHold，解析直接停摆。
  • 无需备案：备案针对境内服务器，GitHub Pages 服务器在境外，.cn 可直接解析。

一、GitHub 侧：登记并验证域名

仓库 → Settings → 左侧 Pages → Custom domain

  1. 在 Custom domain 输入框填 pointwind.cn → Save
  2. 页面随后给出一条 TXT 验证记录：主机记录形如 _github-pages-challenge-point-wind（GitHub 按用户名生成），记录值是页面生成的一串哈希，以实际显示为准。到腾讯云 DNS 解析添加后回来点 Verify
  3. 验证通过后，页面显示 Successfully verified pointwind.cn，Verified domains 列表出现该域名

验证的作用是防止别人把你的域名绑定到他的仓库。域名未验证且 Pages 被关闭时，存在被接管的窗口，因此建议做。

刚 Save 完还没加解析时，页面会显示 DNS check unsuccessful / NotServedByPagesError——这是预期状态，说明 DNS 还没指向 GitHub,不是配置错误，加完解析等几分钟即可。

二、腾讯云 DNS 解析

腾讯云控制台 → 云解析 DNS → pointwind.cn → 添加记录。

这里有个实际限制：免费版对单域名的 A 记录条数有上限，官方建议的 4 条 A 记录放不下。实测下来一条就能跑，所以最终配置精简为三条：

主机记录 记录类型 记录值 说明
@ A 185.199.108.153 顶点域 pointwind.cn，一条即可
www CNAME point-wind.github.io www.pointwind.cn
_github-pages-challenge-point-wind TXT 页面生成的哈希 域名所有权验证，一次性

四条 A 记录（185.199.108.153 至 .111.153）是 GitHub Pages 官方当前的地址，作用是冗余——任一 IP 都能到达站点，多配几条是防止某台服务器故障时仍能解析。额度有限时只配一条不影响可用性，以 GitHub 文档为准。可选再加 AAAA 记录支持 IPv6（2606:50c0:8000::153 等）。

几个操作细节：

  • 主机记录只填前缀。A 记录填 @ 代表域名本身；TXT 的前缀不要带 .pointwind.cn 后缀
  • 记录类型要先切换再填值——TXT 若留着 A 类型，那串哈希会被当成 IP 校验失败
  • 每条填完要点行尾的「确认」才会真正保存，只填不确认不生效
  • 腾讯云若自动生成了默认记录，先删掉再添加
  • 不要用通配符 *.pointwind.cn，存在域接管风险，GitHub 明确不建议

三、HTTPS

回到 Settings → Pages，DNS 生效后页面变为 DNS check successful，此时 Enforce HTTPS 才从灰色变为可勾选。勾选后保存：

证书由 GitHub 自动签发。一个实测现象：勾上 HTTPS 后主域 https://pointwind.cn 立刻返回 200、证书有效，但 https://www.pointwind.cn 会短暂报 SEC_E_WRONG_PRINCIPAL（证书主机名不匹配）。原因是 www 的证书还在签发——nslookup 确认 CNAME 和 A 记录都已正确指向 GitHub，只是证书尚未覆盖 www。等几分钟到几个小时再试即可，不影响主域名使用。

四、Hexo 特有的坑：CNAME 会被部署覆盖

这是本地生成 + 推送模式特有的问题：hexo d 每次把 public/ 强制推成远程 main，如果本地 public/ 里没有 CNAME，GitHub 上那个自动生成的文件就会被删除，自定义域名随即失效。

解决办法是在 source/ 下手动放一个 CNAME 文件，hexo g 时会原样复制到 public/：

放好之后正常 hexo clean && hexo g && hexo d 即可，以后每次部署都会带上它。同理，.nojekyll 也放在 source/ 下——这个目录里的文件不会被 Hexo 清理。

Windows 没有 dig，用 PowerShell 查：

前者应看到 185.199.x.x 的 A 记录，后者返回那条验证哈希——查到即可回 GitHub 点 Verify。注意用 Resolve-DnsName ... -Type TXT 查 TXT；常见的在线”域名解析 IP”工具只查 A 记录，用它验证 TXT 会误报失败。

现象 原因 处理
DNS check unsuccessful / NotServedByPagesError 刚 Save、DNS 还没指向 GitHub 预期状态，加完解析等几分钟
打开是 404 DNS 未生效 / Pages 未绑定域名 等几分钟；确认 Custom domain 已 Save
主域 HTTPS 正常，www 报证书错误 www 证书还在签发 确认 CNAME 已解析，等几分钟到几小时
证书无效或选项一直灰着 证书还在签发 最多等 24 小时

couldn't find the TXT record 验证记录没加对 核对主机记录和值，TXT 生效也需要时间
腾讯云提示”子域名解析异常” 指向海外 IP 的误报 解析本身正确，忽略即可

解析记录全球生效最长 24 小时，国内通常几分钟到半小时。等待期间 https://point-wind.github.io 照常访问，不影响博客。

命令总表

复盘：学到的四件事

1. 域名是唯一能带走的资产，不必为少量差价妥协。
GitHub 用户名改不了、平台规则说变就变，但 pointwind.cn 十年后还是我的。而“.cn 还是 .top”这种问题，算完五年账就会发现并不值得纠结——该斟酌的是名字本身，而非后缀。

2. 分清“协议层”和“应用层”，排错效率翻倍。

Connection refused 是网络层，Permission denied 是认证层，unable to auto-detect email 是 Git 配置层，SSL certificate 是协议配置写错。四个报错看似都与 Git 有关，实际没有一个源自 Hexo。先定位报错所在层级再动手，比盲目重装更高效。

3. 国内环境的最优解已经很明确：npm 走镜像，Git 走 SSH 443。
这两项配置完成后，后续大部分网络类报错都不会出现。它们属于建站第一课，应在执行第一条 npm install 之前完成。

4. 先让它跑起来，再让它好看。
最应避免的情况是：在“.cn 还是 .top”“用不用 fnm”“要不要直接上 .com”之间反复纠结，最终搁置。正确的顺序是——先锁定域名、再让本地 localhost:4000 跑起来、最后打出 Deploy done。主题美化、评论系统、SEO、自定义域名，都可以后续从容添加。

写给同样在犹豫的人：不必想清楚“要做一个什么样的博客”才能开始。先发出第一篇即可——哪怕这一篇，就是记录自己如何把它搭起来的。
