Day01 - Flink 安装与入门

学习日期：2026-11-25
参考资料：尚硅谷《Day01-Flink-安装与入门》
本地环境：Flink 2.3.0 + JDK 17（本地模式，未搭集群）

一、Flink 是什么

一句话：Apache Flink 是一个分布式计算引擎，流处理和批处理都能做。

官网对它的定位是”为分布式、高性能、随时可用以及准确的流处理应用程序打造的开源流处理框架”。在大数据计算引擎的演化里，它通常被归为第四代：

代际 代表 特点
第一代 Hadoop MapReduce Map + Reduce 两阶段，复杂算法要多个 Job 串联
第二代 Tez / Oozie（DAG） 支持 DAG，但多为批处理
第三代 Spark Job 内部 DAG，强调实时（本质是微批）
第四代 Flink 真正的流处理，同时支持批、DAG、SQL

和 Spark、Storm 相比，Flink 的特点是高吞吐、低延迟、高性能三者兼顾——Spark 用批处理模拟流，低延迟做不到；Storm 低延迟但吞吐量不够。

典型应用场景：电商实时报表 / 推荐、IoT 传感器采集与报警、物流订单状态实时更新、金融实时结算与异常检测。

二、核心概念：批与流

这是入门最需要吃透的一点，面试也常问。

  • 批处理：有界、持久、大量，适合需要访问全部记录才能完成的计算，一般用于离线统计。
  • 流处理：无界、实时，对通过的每个数据项执行操作，一般用于实时统计。

Flink 的观点是：一切皆流。有界数据集只是无界流的一种特例——

  • 无界流：只有开始没有结束，事件注入后必须立即处理，不能等数据到齐。
  • 有界流：有明确的开始和结束，可以等数据全部注入完再处理，也可以排序。有界流的处理就是批处理。

这就是所谓的流批一体：不是把两套引擎合并，而是用同一套 API 处理有界和无界数据，底层都是流。阿里当年选 Flink 的初衷也正是这个——不想为全量和增量数据写两套代码。

顺带一提，同样跑在 YARN 上，性能排序是 Flink > Spark > Hadoop(MR)，迭代次数越多差距越明显。原因是 Flink 支持增量迭代，能对迭代自动优化。

三、DataStream 任务开发

Flink 提供了多层 API，越往上抽象程度越高、越易用。从 1.12 起支持流批一体后，DataSet API 不再推荐，优先使用 DataStream API——它既支持无界数据（流处理），也支持有界数据（批处理）。

Flink 程序的编码模型固定为五步：

  1. env —— 准备执行环境
  2. source —— 加载数据
  3. transformation —— 数据处理转换
  4. sink —— 数据输出
  5. execute —— 触发执行

有个关键点：Flink 程序是延迟执行的。main 方法执行时只是把算子串成 DAG 图，数据加载和转换都不会真的发生，直到调用 env.execute() 才触发执行。理解这一点，才算真正入门 Flink。

几个容易踩的坑

  • 并行度优先级：提交参数 > 代码中算子/系统设置 > 默认配置。本地演示设 1，输出顺序好看。
  • Lambda 的泛型擦除：在 Flink 2 里用 lambda 写 flatMap 容易触发序列化问题（Could not deserialize stream node），官方文档推荐用静态内部类实现 FlatMapFunction。
  • 外部传参：老的 readTextFile / readFile 已过时，新 API 是 FileSource。自己写的程序要解析 --input 这类参数得自己处理。

四、Standalone 集群安装部署

本节整理自文档，文档以 Flink 1.17 为例（JDK 8/11，不要用 JDK 17）；Flink 2.x 步骤类似，但 JDK 要 17 及以上。我本地没搭集群，以下为要点记录。

Flink 集群安装有两种方式：Standalone 和 YARN。下面以 Standalone 为例。

节点规划

节点 角色

hadoop12 TaskManager
hadoop13 TaskManager

1. 下载解压

下载 flink-1.17.0-bin-scala_2.12.tgz，上传到 hadoop11 的 /opt/modules/，再解压到 /opt/installs/。

几个常用的调优参数：

  • jobmanager.memory.process.size：JobManager 进程总内存，默认 1600M
  • taskmanager.memory.process.size：TaskManager 进程总内存，默认 1728M
  • taskmanager.numberOfTaskSlots：每个 TaskManager 的 Slot 数，默认 1，一般按 CPU 核数设
  • parallelism.default：默认并行度，优先级低于代码和提交参数里指定的值

3. 分发与启动

  • 用 xsync.sh flink 把安装目录分发到另外两台；记得把 hadoop12、hadoop13 的 taskmanager.host 分别改成各自的主机名。
  • 配置环境变量 FLINK_HOME 和 PATH，三台都要 source 一下。
  • 在 hadoop11 执行 start-cluster-flink.sh 启动，用 xcall jps 验证：
    • hadoop11：StandaloneSessionClusterEntrypoint + TaskManagerRunner
    • hadoop12/13：TaskManagerRunner

4. 与 HDFS 结合（HistoryServer）

把 Hadoop 相关的 jar 放进 flink 的 lib/ 目录并分发三台，在 HDFS 上创建 /flink_history/log，然后重启集群。

  • 8081：运行时 WebUI，功能更丰富
  • 8082：HistoryServer，读 HDFS 上的历史任务，服务重启后历史记录还在

5. 提交官方示例的坑

跑官方 WordCount jar 时，如果数据只在本地放了一份，任务会时好时坏——TaskManager 有三台，得把数据分发到所有节点。运行结果只落在某一台的 /home 下（数据量小，一个 slot 就跑完，slot 在哪结果就在哪）。

如果 8082 没内容，按这个顺序排查：没配 jobmanager → 配置没分发 → 没重启集群 → HDFS 没启动 → 没跑新任务 → 等待时间不够（1~3 分钟）。

六、Flink 1.x → 2.x 迁移实测

文档基于 Flink 1.17，但我本地实际用的是 Flink 2.3.0（2026-06 发布的最新稳定版，2.0 已 EOL）。两边确实有不少差异，记录一下。

JDK 要求：Flink 2.x 最低 JDK 17（推荐 17，支持 21），不再支持 Java 8/11。

主要 API 变化：

变化 Flink 1.x Flink 2.x
集合创建 source env.fromElements(...) env.fromData(...)
flatMap 写法 lambda + returns(Types.TUPLE(...)) 静态内部类实现 FlatMapFunction
DataSet API 有（已过时） 彻底移除，统一用 DataStream / Table API
Scala API 有 彻底移除
SourceFunction / SinkFunction / Sink V1 有 移除，改用 Source / Sink V2
新 API — DataStream V2（实验性，暂不建议生产用）
部署模式 Per-Job 移除，SQL Gateway 支持 Application 模式

实测踩坑：

  1. 直接把 1.x 代码搬过来，lambda + returns(Types.TUPLE) 报 Could not deserialize stream node。改用静态内部类后解决。
  2. 用 mvn exec:java 跑会报 ClassNotFoundException: SimpleUdfStreamOperatorFactory——这是 exec 插件类加载器隔离的问题，不是代码问题。IDEA 里右键 Run 不受影响；命令行验证可以 mvn package 打 fat jar 再 java -jar 跑。
  3. slf4j 有个 Failed to load class StaticLoggerBinder 的警告，是绑定提示，不影响结果。

最终 fat jar 跑出的词频结果和 1.17 完全一致，说明今天学的核心模型（编码五步、流批一体）在两个版本上都成立——版本变了，思想没变。

七、小结

  1. 流批一体——有界流是无界流的特例，一套 DataStream API 打通离线和实时。这是 Flink 区别于 Spark 的根本。
  2. 延迟执行——程序只是描述 DAG，execute() 才是真正的开始。
